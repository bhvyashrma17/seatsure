# Decisions log

This file records the judgement calls made while building SeatSure, and why each was made. "Course" means the Semester 3 Kalvium livebooks, summarised in `../concepts.md`.

| # | Decision | Why | Consequence / trade-off |
|---|---|---|---|
| D-01 | **Project: SeatSure** (campus event registration with a hard seat cap, an auto-promoting waitlist and organiser analytics). | Chosen at the checkpoint. It gives each subject a headline demo: optimistic UI and infinite scroll (Full Stack), a race-proof workflow and layered API (Backend), and locking, indexes, window functions and MongoDB (Advanced Database). | Narrow domain, deep implementation. |
| D-02 | **Three npm workspaces: `/client`, `/server`, `/db`.** `/db` (package `@seatsure/db`) holds the schema, migrations, seed, repositories, SQL analytics and MongoDB models. `/server` only imports from `@seatsure/db`. | The brief asks for separable subjects. Putting the data-access layer behind one package boundary also *is* the repository pattern (Backend M2.11): services call `eventRepository.lockForUpdate(...)` and never see SQL. | Services are unit-tested with in-memory fakes (BE-U09…U23), which shows the storage really is swappable. |
| D-03 | **Languages: `/db` is TypeScript, `/server` and `/client` are JavaScript (ES modules).** | Advanced Database M2 teaches Prisma in TypeScript. Backend and Full Stack teach Express and React in JavaScript (Full Stack M3 uses ES modules; Backend M1 uses CommonJS). ES modules are used throughout for one consistent import style. | The server runs with `tsx` (taught in Advanced Database M2.1) so it can import the TypeScript database layer and the generated Prisma client. `nodemon` (Backend M1.9) still drives dev restarts via `nodemon.json`. |
| D-04 | **Prisma ORM 7.10.0 with `@prisma/adapter-pg`, `prisma7.config.ts`, client generated to `db/generated/prisma`.** | This is exactly the version and layout Advanced Database M2.1 sets up. | The generated client is gitignored. `npm run db:migrate` runs `prisma migrate deploy && prisma generate`. |
| D-05 | **PostgreSQL 18** (local Homebrew install), **MongoDB 8 via Mongoose 9**. | Course versions (Advanced Database M1.2 uses PostgreSQL 18; M3 uses MongoDB with Mongoose). | Neon (Postgres) and MongoDB Atlas free tiers are documented as a fallback in the README. |
| D-06 | **Express 5** (current `npm install express`) but the course's `asyncHandler` is kept. | Express 5 forwards rejected promises by itself, but the explicit wrapper is the pattern Backend M2.7 teaches and it also works on Express 4. | `app.set('query parser', 'extended')` is needed because Express 5's default parser doesn't build `answers[tshirt]=M` objects. |
| D-07 | **React 19 + Vite 8, React Router pinned to v6** (`react-router-dom@6.30`). | The course teaches React Router v6 (Full Stack M1.10). v7 exists but changes APIs. | — |
| D-08 | **Identity = demo user switcher (`X-User-Id` header).** No passwords. | Authentication (sessions/JWT) is Module 4 in both Backend and Full Stack, so it is outside Modules 1–3. The middleware follows the course's `requireAuth → req.user` contract, and the client's 401 interceptor redirects to a "choose user" page (Full Stack M2.10). | **Not secure by design**, which is acceptable for a demo but clearly documented. Swapping in real auth later only changes `server/src/middleware/auth.js`. |
| D-09 | **Concurrency: `SELECT … FOR UPDATE` on the event row under READ COMMITTED**, plus a denormalised `confirmed_count` guarded by `CHECK (confirmed_count <= capacity)`. | The lock serialises "check seats, then take one" per event. Other events are unaffected, so unrelated registrations still run in parallel. SERIALIZABLE would also prevent oversell, but every conflict becomes an error that must be retried. An atomic `UPDATE … WHERE confirmed_count < capacity` alone wouldn't also serialise the duplicate check and the waitlist position. | Proven by DB-T04 (no lock → oversold) vs DB-T05 (lock → exact), BE-I21 (50 requests, 3 seats) and the live demo. Transient failures (deadlock, serialisation, pool timeout) are retried with backoff (BE-U13). |
| D-10 | **Partial unique index for "one active registration"** instead of a plain `UNIQUE(event_id, user_id)`. | Keeps cancelled rows as history (analytics, audit) while still blocking duplicates. | Re-registering after cancelling creates a new row (DB-C08). |
| D-11 | **Transactional outbox for MongoDB writes, with a UUID idempotency key** (`outbox_events.message_id`). | This is the dual-write problem from Advanced Database M3.19. Each message is written in the same transaction as the registration, and the dispatcher delivers it at least once with retry and backoff. Subscribers ignore duplicates via a unique `outboxId`. The UUID was added after **test BE-I25 found a real bug**: re-seeding restarts the bigint ids at 1 while a persistent MongoDB still remembers `outboxId "1"`, so new notifications were silently treated as duplicates. | MongoDB is eventually consistent (it lags by about a second). If MongoDB is down, nothing is lost (BE-I25). The seed also clears a configured MongoDB. |
| D-12 | **The pg pool sets the session time zone to UTC** (`options: '-c timezone=UTC'`). | A probe on this IST machine showed the driver adapter sends timestamps without an offset, so PostgreSQL stored `00:00Z` as `18:30Z` of the previous day. Prisma read it back "correctly", which hid the bug, but SQL using `now()` was 5½ h off. | Regression test DB-Q11. All display code converts to IST (`Asia/Kolkata`), and SQL day boundaries use `AT TIME ZONE 'Asia/Kolkata'`. |
| D-13 | **Partial indexes are declared in `schema.prisma` with the `partialIndexes` preview feature.** CHECK constraints live in a hand-written migration. | Prisma 7.10 can express partial and GIN indexes but not CHECK constraints. Declaring the indexes in the schema stops a future `migrate dev` from dropping them. | Uses a preview feature (documented). |
| D-14 | **No views, stored procedures or triggers.** | They do not appear in Advanced Database Modules 1–3 (indexes, constraints, JSONB, transactions, window functions, CTEs and EXPLAIN do). Business logic stays visible in the service layer, where Backend M2.10/M3.2 says it belongs. | Analytics use CTEs and window functions through `$queryRaw` (Advanced Database M2.19) instead of views. |
| D-15 | **The category composite index is kept, even though the planner often ignores it.** | EXPLAIN showed that for common categories the plain `starts_at` partial index plus a filter is just as good. For a rare category (≈2 %) the composite index is 4× faster (DB-I02). This is reported honestly in the Advanced Database report. | Small extra write cost on inserts. |
| D-16 | **The benchmark runs `VACUUM ANALYZE` after bulk loading.** | EXPLAIN showed the new GIN index was not used: bulk-inserted entries sit in GIN's "pending list" until VACUUM merges them (493 buffers vs 2). | A real-world lesson on index maintenance, included in the report. |
| D-17 | **MongoDB in development: the npm-distributed `mongodb-memory-server` when `MONGODB_URI` is empty.** On start, the outbox is replayed so the in-memory MongoDB is rebuilt from PostgreSQL. | The brief allows an npm-distributed database build for development and tests, and nothing has to be installed. Rebuilding also demonstrates "PostgreSQL is the source of truth". | First start downloads about 77 MB. Data in the in-memory MongoDB resets on every restart (by design). Atlas or a local mongod is used in "real" mode. |
| D-18 | **Testing tools: Vitest, Supertest, React Testing Library, jsdom, mongodb-memory-server.** | Modules 1–3 test with Postman, psql and DevTools, but the brief requires automated tests. These are tooling glue, not features. Backend M1.9 already names jest as a typical devDependency. Vitest is its Vite-native equivalent. | 138 automated tests (47 database + 64 backend + 27 client). |
| D-19 | **Headless Chrome screenshots via `puppeteer-core`, run from outside the project.** | Reproducible report images of the running app. The tool is not a project dependency, so the reports don't have to justify it. | — |
| D-20 | **Plain CSS with design tokens, no CSS framework.** | The course doesn't mandate one. Fewer dependencies to justify, and fully responsive (390 px screenshots). | Supports light and dark mode via `prefers-color-scheme`. |
| D-21 | **Development-only `/api/v1/dev/mongo/{outage,restore}` routes** (organiser only, never mounted when `NODE_ENV=production`). | Makes the graceful-degradation demo (Backend M3.11) a single click. | Clearly marked "development only" in the UI. |
| D-22 | **CSV export neutralises spreadsheet formulas** (prefixes `= + - @` with `'`). | Defensive programming (Backend M3.3): attendee answers are user input and the file is opened by organisers in Excel or Sheets. | Test BE-U38. |
| D-23 | **Concept tags use `// [SUBJECT Mx.y: Concept]`**, e.g. `[BACKEND M2.4: Middleware pipeline]`. | The format requested in the brief, with the lesson number added so every claim in the reports points to one livebook lesson. | `grep -rn "\[BACKEND M"` lists every Backend concept in the code. |
| D-24 | **Seed data is deterministic** (fixed PRNG seed). It uses fictional names and the reserved `example.edu` domain, and creates one event starting about 1 hour after seeding. | Same data on every machine. No real people or domains. The "starts soon" event makes the check-in window demoable on any day. | Re-run `npm run db:seed` on demo day. |
| D-25 | **Proposal lists several concepts per subject** (grouped by module) rather than the single concept per subject the form's description suggests. | The brief says "one or more per subject" and rewards depth. Every listed concept is implemented, tagged in code and tested. | More for the viva to cover, which is handled by the viva prep sheet. |
| D-26 | **Out of scope (later modules):** real authentication, rate limiting, Redis caching (Advanced Database M4), vector search (M5), Docker/CI/deployment (Full Stack M5). | Stays within Modules 1–3 as the brief requires. | Listed as "future work" in the reports. |
